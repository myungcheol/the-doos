# T021 후속 수정 요청 티켓

상태와 선행 관계는 [티켓 원장](../tickets.md)을 따른다. 각 티켓의 산출물을 사용자에게 검수받은 뒤 완료한다.

<a id="t021-01"></a>

## T021-01 — 수정 요청 제출

- 선행 작업은 T021 로그인·권한과 T022 대상 선택·근거 조회다.
- 설명은 로그인한 사용자가 원문을 확인하고 수정안을 제출하는 기능이다.
- 범위는 기존 인물·사실의 값 수정과 인물·사실·혼인·부모 자녀 관계의 추가 또는 제외 제안이다. 요청자는 이유와 스캔 근거 또는 참고 URL을 함께 입력한다. 첨부 근거의 초기 형식은 텍스트와 URL이다.
- 산출물은 요청 테이블의 up/down 마이그레이션, 데이터 사전, 제출 폼과 API, 제출 결과 화면, 권한·입력 검증이다.
- 완료 조건은 요청이 대기 상태로 저장되고 요청 번호를 반환하는 것이다. 요청 내용에는 대상 ID, 작업 종류, 제안값, 서버가 읽은 요청 당시 값, 요청자와 근거가 남는다. 족보 현재값의 변경은 승인 시 수행한다.
- 검증은 비로그인 제출 거부, 클라이언트의 요청자·상태 위조 거부, 없는 대상이나 허용되지 않은 필드 거부, 동일 제출 재전송의 중복 방지, 요청 여러 항목의 원자적 저장, 제출 후 족보 현재값 보존이다.
- 사용자 검수는 로그인 후 이름 수정안을 제출하고 요청 번호·제안값·원문 근거가 조회되는지 확인한다.

### 데이터와 제출 계약

| 저장 대상 | 내용 |
|---|---|
| `change_requests` | 요청자 ID, 이유, 상태, 생성·처리 시각, 처리자·처리 의견, 제출 중복 방지 키 |
| `change_request_items` | 요청 ID, 항목 순서, 대상 종류·ID, 추가/수정/제외 작업, 당시 값, 제안값, 근거 |

상태는 pending·approved·rejected·cancelled로 정의한다. 요청당 여러 항목을 허용하며 최초 구현은 요청 전체를 함께 승인하거나 반려한다. 새 인물에 사실이나 관계를 함께 제안할 때는 요청 내부 임시 ID를 사용하고 승인 시 실제 ID로 연결한다. 관계의 두 끝점은 기존 인물 ID 또는 해당 요청의 새 인물 임시 ID를 참조한다.

당시 값은 클라이언트가 보내는 값을 신뢰하지 않고 서버가 조회해 기록한다. 필드별 타입·허용 범위와 작업 종류를 검사한다. 일반 사용자 세션은 자료 직접 수정 권한을 얻지 않는다.

<a id="t021-02"></a>

## T021-02 — 내 요청 조회·취소

- 선행 작업은 T021-01이다.
- 설명은 제출자가 자기 요청의 처리 결과를 확인하고 대기 요청을 취소하는 기능이다.
- 범위는 내 요청 목록·상세, 상태별 조회, 관리자 처리 의견 표시, pending 요청의 취소다. 정정된 제안은 기존 대기 요청을 취소한 뒤 새 요청으로 제출한다.
- 산출물은 목록·상세 UI와 조회·취소 API, 페이지 단위 목록 조회, 권한·상태 전환 검증이다.
- 완료 조건은 사용자가 자기 요청과 각 제안 항목, 처리 상태·의견을 볼 수 있고 대기 요청을 취소할 수 있는 것이다. 취소된 요청 내용은 이력으로 보존한다.
- 검증은 다른 사용자 요청 ID로 조회·취소 시 거부, 승인·반려된 요청 취소 거부, 반복 취소의 안전한 처리, 취소와 승인 동시 요청에서 한 상태 전환만 성공하는지 확인한다.
- 사용자 검수는 요청 제출 후 목록에서 찾아 취소하고, 새로고침 후에도 취소 상태와 원래 제안 내용이 보이는지 확인한다.

<a id="t021-03"></a>

## T021-03 — 관리자 요청 검토·승인·반려

- 선행 작업은 T021-01·T021-02와 T023·T024의 인물·사실·관계 편집 처리다.
- 설명은 관리자가 수정안과 원문을 비교하고 승인한 내용만 현재 자료에 반영하는 기능이다.
- 범위는 관리자 대기 요청 목록·상세, 요청 당시 값·현재값·제안값 비교, 스캔 근거 이동, 전체 승인·반려와 처리 의견, 충돌 표시다.
- 산출물은 검토 UI, 승인·반려 API, 기존 편집 처리와 요청 이력의 연결, 트랜잭션·동시성 검증이다.
- 완료 조건은 승인 시 자료 변경·기존 변경 이력·요청 상태가 한 트랜잭션으로 저장되는 것이다. 승인자는 로그인 세션에서 정하고 요청 ID와 제안자 ID를 이력에 연결한다. 반려는 이유를 남기고 요청 상태를 변경한다.
- 검증은 비로그인·일반 사용자 승인 거부, 요청 이후 대상 수정·제외·삭제 시 충돌 검출, 동시에 두 번 승인해도 한 번만 반영, 취소 요청 승인 거부, 중간 실패 시 전체 롤백, 잘못된 관계·계보 순환 거부, 승인 후 OCR 재적재에서 검수값 보존이다.
- 사용자 검수는 정상 요청 하나를 승인해 족보에 반영되는지, 다른 요청을 반려해 제안자에게 의견이 보이는지, 이미 수정된 항목의 요청에서 충돌이 표시되는지 확인한다.

승인할 때 대상과 요청을 잠그고 당시 값과 현재값을 비교한다. 충돌하면 pending 상태를 유지하며 충돌 이유를 보여준다. 관리자는 요청을 반려하고 정정안을 받거나, 필요한 내용을 직접 편집 기능에서 반영한다. 요청 승인 경로는 T023·T024의 검증·이력·자동 덮어쓰기 방지 처리를 재사용한다.

## 진행 순서

T021 → T022 → T021-01 → T021-02 순서로 제출·조회 흐름을 구현할 수 있다. T021-03은 T023·T024의 편집 처리까지 준비된 뒤 진행한다. 각 티켓이 리뷰 가능한 크기를 넘으면 작업 시작 전에 기능별로 더 나누고 원장에 기록한다.
